PLG for the Agent Era

Part 3: Onboarding Agents

Kat Laszlo · June 1, 2026

In Part 1, I laid out how agents are reshaping B2B buying. In Part 2, I covered whether agents can even read your site. But being findable and being usable are two different problems. An agent can discover your product, parse your docs, and recommend you to a buyer, and then hit a CAPTCHA on the signup page.

That's where most products are today. The discovery layer is catching up (llms.txt, markdown serving, structured data), but the action layer hasn't moved. Signup, auth, payments, account management: all of it still assumes a human in a browser. And the gap between "an agent can read about your product" and "an agent can actually use your product" is where the next wave of competitive advantage sits.

What agents can't get past

When an agent tries to go from evaluating your product to actually using it, it runs into a predictable set of walls. CAPTCHAs and browser fingerprinting are the obvious ones, but the subtler blockers are just as common: email verification loops (agents don't have inboxes by default), SMS OTP, OAuth consent screens that require a browser session, and "contact sales" gates that kill the entire self-serve path.

These aren't edge cases. They're the default experience at most SaaS companies. A product can have a full REST API and still be functionally inaccessible to agents if the only way to get an API key is through a dashboard that requires email verification and a CAPTCHA.

The Netlify pattern is instructive here. Their `netlify deploy --allow-anonymous` command lets agents deploy without creating an account first, with a one-hour claim window for the human to associate the deployment with their account later. Agents now make up 80% of their new signups. They didn't get there by adding an API on top of their existing flow. They inverted it: deploy first, claim later.

Five dimensions of agent readiness

If readability (Part 2) was about whether agents can find and understand your product, this is about whether they can act on it. The surface breaks down into five dimensions:

DimensionWhat it answers
OnboardingCan an agent create an account without a browser?
AuthenticationCan it get scoped credentials programmatically?
PurchasingCan it select a plan and pay without a checkout page?
Usage monitoringCan it track consumption and costs via API?
Self-managementCan it upgrade, downgrade, or cancel without a dashboard?

Most products score well on zero or one of these. Having a REST API doesn't mean you score well on any of them, because the API usually covers your product's core functionality, not the account lifecycle around it. You might have a beautiful API for your product's features but require a human to click through Stripe Checkout to start paying for it.

Who's actually doing this

A handful of companies have built the full stack. They're worth studying not because every product needs to match them, but because they show what the end state looks like.

Cloudflare lets agents create accounts, buy domains, and deploy applications end-to-end. No browser, no human intervention beyond initial terms acceptance. They went from "agents can use our CDN" to "agents can provision entire infrastructure stacks" in about a year.

Stripe built the Agentic Commerce Protocol and launched Stripe Projects, where agents get scoped API keys, discover services from a catalog, and pay via the Payments API. It's invitation-only with 32 launch partners, but the protocol itself is open and points to where programmatic commerce is heading.

Twilio is the quietest example but arguably the deepest. API coverage for account creation, number provisioning, usage records, and billing, with most lifecycle actions available programmatically. They didn't build this for agents specifically; they built it because developers wanted it, and agents are just very fast developers.

The common thread isn't technology. It's a philosophy: every action a human can take in a dashboard should have a programmatic equivalent. Products that were built API-first for developers end up being agent-ready almost by accident. Products that bolted APIs onto dashboard-first experiences have gaps everywhere.

Most agent auth is a pasted API key

Authentication is where the most interesting tension sits. The recommended approach for agent-to-service auth is OAuth 2.0 Client Credentials (machine-to-machine tokens with scoped permissions and short TTLs). It's the "right" answer, and almost nobody implements it for self-serve tiers.

What actually happens is simpler and messier: the human generates an API key in a dashboard and pastes it into the agent's configuration. That key typically has full account access, no expiration, no budget limits, and no record of which agent is using it. By one estimate, 93% of AI agent projects use unscoped API keys. One leaked key, one runaway agent, and the entire account is exposed.

The practical middle ground is scoped keys with budgets. The human still creates the key (you don't need to solve programmatic onboarding on day one), but the key itself carries constraints: which endpoints it can hit, how much it can spend, and when it expires. This is what I built with agentkey, an npm package that adds scope, budget, and expiry controls to API keys.

Account: Acme Corp (Pro plan, $100/month)
  |
  |-- ak_sales_...     scopes: [proxy.chat]          budget: $40/mo
  |-- ak_analytics_..  scopes: [usage.read]           budget: $0
  |-- ak_agent_...     scopes: [proxy.chat, usage.read]  budget: $30/mo  expires: 7d

The account's plan sets the ceiling. Keys subdivide it. No single key can blow the whole month's budget. The human sets the guardrails, and the agent operates within them. This is different from giving every agent the same master key and hoping nothing goes wrong.

I built agentkey because the gap between "just use OAuth" and "here's an unscoped API key, good luck" was too wide. Most teams aren't going to implement a full Client Credentials flow for their self-serve tier. But they can add four columns to their API keys table and start enforcing budgets tomorrow.

Payments without a checkout page

Purchasing is the dimension where the gap between recommended and practical is widest. The gold standard is Stripe's Agentic Commerce Protocol: agents discover plans from a machine-readable catalog, select one, and pay using the Payments API with a pre-authorized payment method. No Checkout Session, no redirect, no browser.

But Stripe's full protocol is invitation-only, and most products aren't going to build a custom billing API. The practical path starts with something most SaaS companies already have: Stripe's saved payment methods. The human adds a card once through the normal checkout flow. After that, an agent can use `POST /v1/subscriptions` with the saved `pm_...` token to change plans programmatically. No new billing infrastructure required, just an API route that wraps what Stripe already provides.

There are also emerging primitives worth watching. Shared Payment Tokens (SPTs) are scoped, time-limited payment authorizations that work across merchants. The HTTP 402 protocol (x402) enables pay-per-request micropayments. Stripe Issuing can generate virtual card numbers with per-transaction spend controls for agents. None of these are mainstream yet, but they point to a world where agent purchasing is as routine as agent browsing.

The machine-readable pricing layer matters too. If an agent can't programmatically compare your plans, features, and limits, it can't make a purchasing decision without asking the human to read a pricing page. Publishing a `pricing.json` (a structured manifest of your plans, like `robots.txt` for pricing) lets agents compare you against competitors without parsing marketing copy. I published a schema for this in the agent-serve repo, and including it moves a product from a 3 to an 8 on the purchasing dimension of an audit.

The audit

I built agent-serve as a Claude Code skill that audits these five dimensions and scores each one 0-10. It works in two modes: URL mode (fetches your marketing site, docs, and API references) and repo mode (analyzes your API routes, auth middleware, and billing integration from source).

The scoring anchors are concrete. A 0 on onboarding means browser-only signup with CAPTCHA. A 5 means API signup exists but with friction (email verification, manual approval). A 10 means Cloudflare-style zero-friction provisioning where an agent can go from nothing to a working account in one API call.

Most products I've audited land between 1 and 3 across all five dimensions. They have APIs for their core features but nothing for the account lifecycle. The signup requires a browser. The API key requires a dashboard. The payment requires Checkout. The plan change requires support. Each of these is a wall an agent can't get past.

The maturity model looks like this:

LevelWhat it means
0: Agent-hostileBrowser-only everything, CAPTCHA, "contact sales"
1: API existsREST API for features, but signup/auth/billing require a human
2: Agent-possibleAPI signup (with friction), scoped keys, usage visible via API
3: Agent-friendlyFull programmatic onboarding, plan selection and payment via API
4: Agent-firstZero-friction provisioning, MCP server, spending policies, self-serve everything

Level 4 is Stripe and Cloudflare. Level 2 is a reasonable near-term target for most self-serve SaaS. The jump from 1 to 2 is the highest-leverage work: add an API signup route, scope your API keys, and expose usage data. None of that requires rebuilding your billing system.

Does this matter yet?

The same honest framing from Part 2 applies here. If you're optimizing for agents to discover you, the evidence is mixed. If you're optimizing for agents to use you once they arrive, the evidence is stronger but the market is early.

Netlify's 80% agent signup rate is real, but Netlify is a developer tool where the users are already in terminals and the agents are coding agents deploying projects. That's the ideal case. A marketing automation platform or a CRM probably isn't seeing 80% agent signups anytime soon.

But the directional bet is clear. Stripe didn't build an entire commerce protocol for a market that doesn't exist. Cloudflare didn't rebuild their onboarding around agents as a thought exercise. And the 73% of B2B buyers using agents for research will eventually expect those agents to act on their behalf, not just report back.

The pragmatic path is to start with Level 2. Scope your API keys (or use something like agentkey to add scoping to what you have). Expose usage data via API. Add a machine-readable pricing manifest. These are hours of work, not quarters, and they position you for the transition without requiring you to rebuild your entire account lifecycle.

Run agent-serve on your product to see where you stand. Then fix the highest-leverage dimension first. For most products, that's auth (scoped keys) or onboarding (an API signup route). The rest can follow as the market demands it.
